# Experiment 02 — Concurrency and throughput

Benchmark the OpenAI-compatible vLLM streaming chat API under varying concurrency.

## Setup

Start the model using `../01-vllm-setup/serve.sh`. Then:

```bash
python -m pip install -r 02-throughput-benchmark/requirements.txt
python 02-throughput-benchmark/benchmark.py --concurrency 1 5 10 25 50 100 --requests-per-level 100 --max-tokens 200 --output 02-throughput-benchmark/results/run.csv
```

Increase to `200 400 800` only after validating that the server can tolerate the load. Concurrency means **simultaneous in-flight requests**, not sustained user count.

## Measurements

- TTFT: seconds until the first non-empty generated text delta (not HTTP response headers)
- End-to-end latency: seconds from request start to stream completion
- Output throughput: total completion tokens divided by elapsed wall-clock seconds
- Error rate and P95 latency

Token counts use streamed API `usage.completion_tokens` when supplied. Otherwise a run is marked as lacking exact output-token counts; the script does **not** pretend character counts are token counts.

The benchmark warms up the server, runs a fixed number of requests per level, and writes per-level CSV summaries. For stronger conclusions, run multiple repetitions with fixed input/output lengths and inspect server-side metrics. Streaming and load generation from the same machine may affect measurements.

## Previously discussed observations

An earlier experiment reported a peak near 400 concurrent requests (~10,372 output tokens/sec) and lower throughput at 800 (~9,649). These are **historical observations from the conversation**, not results generated by this repository's script. No raw per-request benchmark logs were available for verification; rerun the benchmark before publishing reproducible numbers.

## Note on GPU memory

More concurrency can increase KV-cache demand, but this experiment alone cannot establish whether KV-cache pressure caused a particular throughput decline.
